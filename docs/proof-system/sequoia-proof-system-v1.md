# Sequoia Proof System, version 1.0

Published: August 29, 2026

Owner: Sequoia GEO
Public explanation: `/proof-system`

## Position

> We establish what is true, correct what is broken, and verify the result before we call it marketing success.

This standard governs new and revised Sequoia assessments, proposals, case studies, client reporting, sales proof, AI Search Evidence System outputs, and Knowledge Interface answers when released. Existing public proof is migrated as records and publication permissions are confirmed.

## Why this exists

Marketing work commonly produces several different kinds of evidence:

- A system condition can be observed.
- A defect can be corrected.
- The correction can pass a technical check.
- A platform can report activity.
- A real person can submit an inquiry.
- A qualified lead can be established.
- The operating business can confirm a job booked.

Those events are related, but they are not interchangeable. The Proof System prevents a later-stage label from being applied before the required evidence exists.

## Operating sequence

1. **Establish what is true.** Preserve the starting condition, source, definition, date range, read date, and limitation. If a baseline was off or unavailable, record it as unavailable.
2. **Correct what is broken.** Name the defect, document the change, and separate Sequoia's work from strengths the business already had.
3. **Verify the result.** Define and run an acceptance check. Record whether the check passed, failed, or remains open.
4. **Report only what follows.** Apply the narrowest accurate status. State what the evidence does not establish.

## Proof statuses

| Status | Required evidence | Does not establish |
| --- | --- | --- |
| Baseline verified | Dated public, platform, account, or operating record | That Sequoia created the condition or that it remains current |
| Correction completed | Named defect, dated change, and implementation record | Traffic, inquiries, qualified leads, or jobs booked |
| Verification passed | Stated acceptance check and retained result | Causation or a later business outcome |
| Observed after | Dated measurement collected after the work | That the work caused the movement |
| Client confirmed | Business confirmation of an inquiry, qualified lead, or job booked under a stated definition | Identity-level source attribution unless the records are joined |
| Not established | Recorded evidence gap or failed verification | Anything beyond the stated gap |

## Evidence classes

| Class | Use |
| --- | --- |
| Directly measured | Read by Sequoia from a named system, report, or retained artifact |
| Client attested | Confirmed by the operating business, but not independently read from the underlying system |
| Inherited strength | Real before Sequoia became involved, and retained only as starting context |
| Public observation | Visible on a public surface on a recorded date |
| Reconstructed | Assembled from partial records or later recollection, never used as headline proof |
| Unavailable | The necessary evidence was not retained, cannot be accessed, or does not exist |

## Claim record

Every published numerical or outcome claim must include:

- Claim ID
- Client or subject
- Exact statement
- Proof status
- Evidence class
- Source label
- Metric definition
- Date range
- Read date
- What the claim does not establish
- Publication permission: named, anonymized, or internal only
- Causal design: none, pre-post, holdout, or controlled panel
- Re-verification date when a mutable condition is presented as current

A dated historical observation does not expire. A mutable condition described as currently true must carry a future re-verification date.

The default causal design is `none`. Timing alone does not establish causation.

## Outcome ladder

1. System condition
2. Correction
3. Verification
4. Platform activity
5. Inquiry
6. Qualified lead
7. Job booked

Promoting a record requires the evidence for the next stage. Platform labels do not override Sequoia's stage definitions.

## Public case-study format

Every new case study uses these blocks in this order:

1. Header and publication status
2. Starting conditions, with inherited strengths separated from defects
3. Agreed scope
4. What Sequoia completed
5. What was verified
6. What is not established
7. What remains open or comes next
8. Evidence footer with sources, dates, approval, and material connection

If the work is credible but has no verified business outcome, label it an implementation record, engagement spotlight, or field note. Do not force it into a results case study.

## Refusal rules

Sequoia does not publish:

- Client revenue as Sequoia proof
- Platform activity labeled as a customer
- An AI citation labeled as a recommendation
- A manufactured before-and-after result when the baseline was off or unavailable
- A causal claim based on timing alone
- An inherited rating, review count, or search position as an outcome Sequoia produced
- A named client, shaped quotation, or private operating detail without publication-aware permission
- Competitor blame when the evidence supports only a defect or incomplete handoff

## Release gate

Before a claim is published:

1. Confirm the claim record is complete.
2. Confirm the record contains at least one affirmative, evidenced fact about the work or condition.
3. Re-read the cited source and verify the metric definition and date range.
4. Confirm any mutable public condition again.
5. Confirm permission for the company name, quotation, and operating detail separately.
6. Put the limitation in the same visual field as the claim when readers could otherwise infer more.
7. Run the public claims and proof-system tests.
8. Review the complete page for its net impression, not only sentence-level accuracy.
9. Record approval and publication date.

## Versioning

Material definition changes require a new version and public changelog entry. A prior report keeps the definitions that applied when it was issued. Later evidence can update a future report but does not silently rewrite the prior one.
